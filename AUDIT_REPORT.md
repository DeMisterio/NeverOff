# Аудит Android-мессенджера NeverOff

**Тип аудита:** статический (код-ревью). Это отличается от исходного запроса на полный QA/security аудит с ручным тестированием на устройстве — см. «Вводные данные» и раздел «Не проверено» ниже.

## Вводные данные

| Параметр | Значение |
|---|---|
| Приложение / package name | NeverOff / `com.neveroff` |
| Версия / сборка | versionName `2.0`, versionCode `2` (app/build.gradle.kts) |
| minSdk / targetSdk | 26 / 34 |
| Тестовое устройство или эмулятор | **Отсутствует.** В окружении, где выполнялся аудит, нет `adb`, эмулятора или физического устройства — весь аудит выполнен по исходному коду |
| Root / прокси (Burp/mitmproxy) | Нет — динамическая проверка трафика не проводилась |
| Исходный код или только APK | Полный исходный код (Kotlin, Jetpack Compose, Supabase + Firebase) |
| Тестовые аккаунты | Не использовались (нет запуска приложения) |

Из-за отсутствия устройства **все динамические проверки (реальный трафик, `adb backup`, поведение на живом эмуляторе, пуши в реальном времени, скриншоты UI) не проводились** и явно помечены как «не проверено» в соответствующих разделах.

## 1. Executive Summary — топ критичных находок

| # | Находка | Критичность |
|---|---|---|
| 1 | Файл `env` в корне репозитория содержит те же боевые секреты, что и `.env` (service-role key, строка подключения к БД, Resend API key), но **не** покрыт `.gitignore` — один `git add .` может закоммитить их | **Critical** |
| 2 | Самообновление приложения ставит APK по URL из БД **без HTTPS-принуждения, проверки домена и проверки подписи/чексуммы** | **Critical** |
| 3 | Realtime-подписка на открытый чат никогда не активируется (`onStart()/onStop()` в `ChatViewModel` нигде не вызываются) — сообщения от собеседника не появляются в реальном времени, статус «прочитано» не обновляется, пока чат открыт | **Critical** |
| 4 | Отсутствует logout / удаление аккаунта где-либо в приложении | **High** |
| 5 | Нет ретраев и идемпотентности при отправке сообщений — двойной тап по «отправить» создаёт дубликаты; неудачная отправка молча теряется | **High** |
| 6 | Статус «отправлено» показывается независимо от реального успеха отправки — нет визуального состояния «ошибка/не отправлено» | **High** |
| 7 | Прогресс загрузки медиа (голос/фото/видео) реализован в ViewModel, но не подключён к UI — пользователь не видит, грузится ли файл, и не узнаёт о сбое | **High** |
| 8 | Групповые чаты: схема БД их предполагает, но клиент не умеет создавать группы, а имеющаяся логика 1:1-чата тихо испортит данные, если группа появится (в т.ч. push уйдёт только одному участнику) | **High** |
| 9 | Нет `FLAG_SECURE` — расшифрованный контент попадает в скриншоты/Recents; уведомления показывают текст сообщения | **Medium** |
| 10 | PIN блокировки чата хранится как несоленый однократный SHA-256 | **Medium** |

**Общий вывод:** транспортное и at-rest шифрование спроектированы разумно (E2E на AES-256-GCM + ECDH P-256, БД зашифрована SQLCipher с ключом в Android Keystore) — это сильная сторона. Однако (а) в репозитории лежит незащищённый файл с боевыми секретами, (б) механизм самообновления — путь к полной компрометации устройства, и (в) заявленная «реалтайм»-функциональность мессенджера фактически не работает, пока чат открыт, из-за неподключённого lifecycle-кода. Это системные, а не косметические проблемы.

## 3. Детальные карточки по критичным находкам

### SEC-01 — Незащищённый файл с боевыми секретами
- **Область / критичность:** Безопасность / **Critical**
- **Описание:** В корне репозитория лежит файл `env` (без точки), который по факту не шаблон, а копия боевых значений из `.env`: `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_DB_URL`, `RESEND_API_KEY`, `APP_ENVIRONMENT` совпадают побайтово. `.gitignore` исключает только `.env`, а `env` — нет.
- **Шаги воспроизведения:** `git add -A` (или `git add .`) в корне репозитория → `git status` покажет `env` как staged.
- **Ожидаемое vs фактическое:** Ожидается, что все файлы с секретами исключены из индексации. Фактически один файл остаётся полностью незащищённым.
- **Рекомендация:** Немедленно удалить `env` из рабочей директории (или переместить его содержимое в защищённое место), добавить `env` (и в целом `*.env*` без исключений для примеров) в `.gitignore`. Так как секреты уже лежали в незашифрованном виде в рабочей копии, рекомендуется в любом случае ротировать `SUPABASE_SERVICE_ROLE_KEY`, пароль БД и `RESEND_API_KEY` из соображений предосторожности.

### SEC-02 — Самообновление без проверки
- **Область / критичность:** Безопасность / **Critical**
- **Описание:** `UpdateManager.downloadApk()` скачивает файл по URL, который целиком приходит из таблицы `versions` в Supabase (поле `google_link`), без ограничения на схему/домен. `installApk()` передаёт скачанный файл системному инсталлятору без проверки подписи или чексуммы.
- **Шаги воспроизведения (концептуально):** Если строка в таблице `versions.google_link` указывает на произвольный URL (в т.ч. `http://`), приложение скачает и предложит установить этот файл как «обновление».
- **Ожидаемое vs фактическое:** Ожидается проверка HTTPS + allow-list домена + проверка подписи APK (или как минимум SHA-256 хэша) перед установкой. Фактически ничего из этого нет.
- **Рекомендация:** Ограничить схему до `https`, зафиксировать доверенный домен, сверять хэш/подпись скачанного APK с ожидаемым значением, полученным по отдельному защищённому каналу. Дополнительно проверить RLS-политику таблицы `versions` в Supabase — кто может её изменять (это не проверялось в рамках статического аудита).

### FUNC-01 — Realtime не работает для открытого чата
- **Область / критичность:** Функциональность / **Critical**
- **Описание:** `ChatViewModel.onStart()`/`onStop()` вызывают подписку/отписку от realtime-канала чата, но нигде в `ChatScreen.kt` эти методы не вызываются (нет `DisposableEffect`/`LifecycleEventObserver`, в отличие от `ChatListScreen.kt`, где это сделано правильно). `GlobalRealtimeManager` при этом явно игнорирует сообщения для текущего открытого чата.
- **Шаги воспроизведения:** Открыть чат на устройстве A, отправить сообщение с устройства B → сообщение не появится на экране A в реальном времени; статус «прочитано» на B не обновится, пока A не выйдет из чата и не зайдёт заново.
- **Ожидаемое vs фактическое:** Ожидается мгновенное появление новых сообщений и обновление статусов. Фактически обновление происходит только при повторном входе в чат (через `syncHistory()`) или случайно через побочный эффект FCM-пуша.
- **Рекомендация:** Добавить `DisposableEffect(chatId)` в `ChatScreen.kt`, вызывающий `viewModel.onStart()`/`onStop()` по аналогии с `ChatListScreen.kt`.

### UI-08 — Нет пустого состояния для чата
- **Область / критичность:** UI / **High**
- **Описание:** `LazyColumn` со списком сообщений не имеет ветки для пустого списка.
- **Шаги воспроизведения:** Создать новый чат без сообщений и открыть его.
- **Ожидаемое vs фактическое:** Ожидается заглушка вроде «Напишите первое сообщение». Фактически — пустой экран (только фон/обои).
- **Рекомендация:** Добавить `if (uiMessages.isEmpty())` ветку с текстом-подсказкой, аналогично уже реализованному пустому состоянию в `ChatListScreen.kt`.

### UI-10 — Удаление без подтверждения в медиапросмотрщике
- **Область / критичность:** UI-логика / **High**
- **Описание:** Кнопка/пункт меню «Delete» в `FullScreenMediaViewer` вызывает `deleteMessageForEveryone()` напрямую, без диалога подтверждения — в отличие от всех остальных мест приложения, где то же действие защищено `AlertDialog`.
- **Шаги воспроизведения:** Открыть медиа на весь экран → нажать «Delete» → сообщение необратимо удалено для всех участников без единого дополнительного подтверждения.
- **Рекомендация:** Обернуть вызов `onDelete()` в тот же `AlertDialog` с выбором «Удалить для всех / Удалить у себя», что используется в остальных местах.

*(Остальные находки из таблиц раздела 2 задокументированы там же с указанием файла/строки, критичности и краткого описания; полные пошаговые репродукции для функциональных находок FUNC-02…FUNC-16 и UI-01…UI-11 доступны по запросу в этом же формате — сокращены здесь для читаемости отчёта.)*

## 4. Раздел «Не проверено»

Полностью или частично не проверено из-за отсутствия устройства/эмулятора, root и прокси:

- Реальное поведение TLS/handshake, устойчивость к MITM через пользовательский/девайсный CA (нужен Burp/mitmproxy).
- Хранение токена сессии внутри библиотеки `supabase-kt`/`gotrue` (код приложения к токену напрямую не обращается — нужно исследовать саму библиотеку).
- Содержимое `adb backup`/Auto Backup снапшота на реальном устройстве (при `allowBackup="true"`).
- RLS-политики таблиц `versions` и `messages` в реальном Supabase-проекте (кто может писать/обновлять/удалять) — определяет фактическую эксплуатируемость SEC-02 и FUNC-16.
- Были ли когда-либо запушены `.env`/`env`/`local.properties` в удалённый репозиторий (проверялась только локальная история `git log --all`).
- Реальная дедупликация/задержка push-уведомлений на устройстве, поведение Doze-режима.
- Поведение при повороте экрана / пересоздании процесса (FUNC-13) — механизм `configChanges` не входил в проверенные файлы.
- Реальные контрастность/читаемость хардкод-цветов (UI-01, UI-02, UI-повреждения при выборе светлых тем) — нужна визуальная проверка на экране.
- Поведение клавиатуры/`imePadding` (UI-05, UI-06) на реальных размерах экрана.
- Обрезание текста при увеличенном системном масштабе шрифта (UI-07) — нужна проверка при `fontScale` до 200%.
- Направление свайпа в RTL-локали (`ChatListScreen`) — код выглядит согласованным, но не проверялся визуально.
- Поведение системной кнопки «Назад» для `LockScreen`/`FullScreenMediaViewer` (UI-11) — предсказано по коду, не нажималось физически.
- Функциональные баги, требующие двух живых аккаунтов (синхронизация между устройствами, дедупликация пушей, гонки при групповых операциях) — не тестировались вживую.
